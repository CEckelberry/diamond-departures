# Packet P-LIVE-02-RED — Implementation Plan

## 1. Assumptions & Context
*   **Architecture**: The system consists of a `Scanner` (or `Job`) that iterates over "games" or "feeds". It maintains a cursor (`updatedSince`) to ensure idempotency and incremental processing.
*   **Persistence**: The cursor is persisted to a local file (e.g., `cursor.json` or similar). We assume a simple JSON structure: `{ "last_updated": "<ISO-8601>" }`.
*   **Failure Mode**: If the scanner fails to fetch data for a specific game/feed, it must *not* advance the cursor. If the entire scan cycle fails (or specific critical failures occur), the system must track these metrics.
*   **Metrics**: We assume a metrics interface (e.g., Prometheus client or a simple counter/histogram collector) is available to record `lag` and `failure_count`.

## 2. Risks & Edge Cases
*   **Race Conditions**: If two scanner instances run, they might overwrite each other's cursors. *Mitigation*: Tests will focus on single-instance atomicity first. We assume file locking or atomic writes (write-to-temp + rename) are required in the implementation phase.
*   **Clock Skew**: `updatedSince` relies on timestamps. Tests must mock time or use deterministic timestamps to avoid flakiness.
*   **Partial Failures**: If Game A fails but Game B succeeds, does the cursor advance? *Assumption*: The cursor advances only after a *successful* full scan of all items. If any item fails, the cursor is preserved for the next run (retry logic).
*   **File Permissions**: Tests must handle cases where the cursor file exists but is unreadable or corrupted.

## 3. Plan
1.  **Define Test Fixtures**: Create a mock `FileSystem` and `MetricsCollector` to isolate the scanner from I/O and external systems.
2.  **Write Failing Tests**:
    *   `test_checkpoint_load_missing_file`: Verify default cursor (e.g., epoch or null) when file is absent.
    *   `test_checkpoint_save_valid_json`: Verify atomic write and content correctness.
    *   `test_job_uses_checkpoint_cursor`: Verify that if `updated_since` is not provided, the job loads from the checkpoint file.
    *   `test_job_updates_checkpoint_after_success`: Verify cursor is saved only after a successful scan cycle.
    *   `test_job_preserves_cursor_on_failure`: Verify cursor is *not* updated if a fetch fails.
    *   `test_metrics_include_lag_and_failures`: Verify that metrics are recorded correctly during failure scenarios.
3.  **Ensure Tests Fail**: Do not implement the production logic yet. The tests should fail due to missing methods, incorrect defaults, or no persistence.
