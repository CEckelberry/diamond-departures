# Packet P6-03 — Between-games and no-games-today states GREEN

## 1. Plan

### Assumptions
1.  **Architecture**: The frontend is a React application using `react-query` (or similar) for data fetching and a WebSocket client for real-time board updates.
2.  **State Model**: The backend provides a global `GameState` enum: `LIVE`, `BETWEEN_GAMES`, `NO_GAMES_TODAY`.
3.  **Board Component**: The board component (`GameBoard`) is currently tightly coupled to the `LIVE` state, assuming immediate move updates.
4.  **Connectivity**: WebSocket connections are expensive or rate-limited; we must reduce churn during idle states.

### Risks & Failure Modes
1.  **Stale UI**: If the state switches from `BETWEEN_GAMES` to `LIVE` while the user is looking at the "Next Game ETA" screen, the board might not render immediately.
    *   *Mitigation*: Use optimistic UI updates and robust `onOpen`/`onMessage` handlers in the WebSocket hook.
2.  **Memory Leaks**: Keeping the WebSocket open during `NO_GAMES_TODAY` without proper cleanup if the user navigates away.
    *   *Mitigation*: Strict `useEffect` cleanup in the `useGameState` hook.
3.  **Heartbeat Timeout**: The "slower reconnect/heartbeat policy" might cause the client to think the connection is dead if the server doesn't send pings frequently enough during idle states.
    *   *Mitigation*: Adjust the heartbeat interval dynamically based on the current `GameState`.

### Implementation Strategy
1.  **State Management**: Extend the `useGameState` hook to handle `BETWEEN_GAMES` and `NO_GAMES_TODAY`.
2.  **WebSocket Policy**: Implement a dynamic heartbeat/reconnect strategy in `useWebSocket`.
3.  **UI Components**:
    *   Create `IdleStateBanner` for header messages.
    *   Update `GameBoard` to accept an `isActive` prop and render a placeholder or disabled state when not `LIVE`.
    *   Ensure `StatPicker` and sorting logic remain independent of the live game state.
