## Plan with Assumptions + Risks

### Assumptions
1. **Data Model**: Players have unique IDs, timestamps, and view relationships (many-to-many)
2. **Storage**: Players and views are stored in a relational database (PostgreSQL)
3. **Ingest Pipeline**: Uses a job-based architecture where scanner jobs output JSON payloads
4. **Dependencies**: Current codebase has existing scanner job infrastructure and test framework
5. **Delta Logic**: A player is "changed" if any of their views were modified since last scan

### Risks & Edge Cases
- **Race Conditions**: Multiple scanner jobs running concurrently could produce inconsistent deltas
- **Data Loss**: If a player is deleted between scans, we might miss their delta
- **Circular Dependencies**: View updates could trigger player deltas, creating infinite loops
- **Performance**: Large player/view datasets could cause memory issues
- **Idempotency**: Duplicate deltas could cause downstream systems to process same data multiple times

### Implementation Strategy
1. Create `ScannerDeltaHelper` module with methods to:
   - Calculate player deltas (added/updated/removed)
   - Identify affected views for each player
   - Generate deterministic payload structure
2. Integrate helper into existing scanner job
3. Add comprehensive tests covering edge cases
