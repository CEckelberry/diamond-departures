# Packet P-LIVE-04-RED — Reconciliation Cadence + Scanner Telemetry Tests

## 1. Plan, Assumptions, and Risks

### Assumptions
1.  **Existing Architecture**: The system has a `Scanner` component that processes "changes" (incremental updates) and occasionally performs a "full live reconciliation" (scanning the entire state).
2.  **Configuration**: There is a configuration object (likely YAML/JSON/env-driven) that controls the `reconciliation_cadence` (e.g., an integer $N$).
3.  **State Persistence**: The scanner persists a checkpoint file containing a `scan_count` to track how many incremental scans have occurred since the last full reconciliation.
4.  **Telemetry**: The scanner emits telemetry/metrics, specifically including a field for `reconciliation_count` or similar, and potentially logs the `scan_count`.
5.  **Language/Stack**: Python (standard for this type of infrastructure testing), using `pytest`, `unittest.mock`, and standard library `json`/`pathlib`.

### Risks & Edge Cases
1.  **Race Conditions**: If multiple scanner instances run, they might conflict on the checkpoint file. *Mitigation*: Tests will assume single-instance behavior for simplicity unless concurrency is explicitly in scope.
2.  **Clock Skew**: If reconciliation is time-based, tests are fragile. *Assumption*: Cadence is count-based (every Nth scan) as per "every Nth scan triggers full live reconciliation".
3.  **Checkpoint Corruption**: If the checkpoint file is missing or malformed, the scanner should reset `scan_count` to 0. Tests must cover this.
4.  **Off-by-One Errors**: The trigger condition is critical. Is it `scan_count % N == 0`? Or does it trigger *after* N scans? *Assumption*: It triggers when the counter reaches N, then resets. We will test for the boundary condition.
5.  **Telemetry Latency**: Telemetry might be async. Tests must ensure telemetry is flushed or captured synchronously during the test run.

### Implementation Strategy
1.  **Mocking**: Mock the actual "live scan" operation to avoid side effects (e.g., network calls, heavy I/O). We only care that it *was called* at the right cadence.
2.  **Checkpoint Simulation**: Use a temporary directory for checkpoint files to isolate test runs.
3.  **Test Cases**:
    -   `test_cadence_config_default`: Verify default cadence if not specified.
    -   `test_reconciliation_trigger_at_n`: Verify full reconciliation happens exactly at scan N.
    -   `test_no_reconciliation_before_n`: Verify no full reconciliation for scans < N.
    -   `test_checkpoint_persistence`: Verify `scan_count` is saved and loaded correctly.
    -   `test_checkpoint_reset_after_reconciliation`: Verify `scan_count` resets to 0 after a full reconciliation.
    -   `test_telemetry_fields`: Verify telemetry output includes reconciliation metrics.
