# Packet P-LIVE-03-RED — Scanner delta payload tests first

## 1. Plan

### Assumptions
1. **Architecture**: The system uses a `Scanner` that processes game events and produces a `DeltaPayload`.
2. **Data Model**:
   - `Player`: Has an `id`, `score`, and `status`.
   - `BoardView`: Represents a sorted view of players (e.g., "Leaderboard", "Top 10"). It is derived from the global player list via a `LeaderboardMapper`.
   - `DeltaPayload`: Contains `changed_player_ids` (Set<String>) and `affected_view_ids` (Set<String>).
3. **Dependencies**: We assume a standard testing framework (JUnit 5 + Mockito) and a build system (Maven/Gradle). The implementation classes (`Scanner`, `LeaderboardMapper`, `DeltaPayload`) are assumed to exist but may be stubs or incomplete.
4. **Edge Cases**:
   - No changes: If no players change, the payload should reflect empty sets.
   - View invalidation: If a player leaves the top N, views covering that rank must be invalidated.
   - Concurrent updates: Not tested here (focus on single-threaded delta generation).

### Risks & Failure Modes
1. **False Positives**: Tests pass if `DeltaPayload` fields are not properly populated. *Mitigation*: Explicitly assert field contents.
2. **Mocking Leakage**: Over-mocking `LeaderboardMapper` might hide integration issues. *Mitigation*: Use real mapper in tests where possible, or mock only external dependencies.
3. **Idempotency**: Re-processing the same event should not produce duplicate deltas. *Mitigation*: Test sequential updates.

### Implementation Strategy
1. Create `ScannerDeltaPayloadTest.java`.
2. Write test cases:
   - `testEmptyUpdateProducesEmptyDelta`: No changes → empty payload.
   - `testScoreChangeUpdatesChangedPlayerIds`: Score change → player ID in `changed_player_ids`.
   - `testRankChangeInvalidatesAffectedViews`: Rank change → view IDs in `affected_view_ids`.
   - `testMultipleChangesAggregateAll`: Multiple players change → all IDs aggregated.
