# Packet P7-02 — Accessibility Pass GREEN: Implementation Plan & Edits

## 1. Plan, Assumptions & Risks

### Assumptions
1.  **Framework**: The project uses Svelte (implied by `svelte-check` and `.svelte` file extensions).
2.  **Component Structure**: There is a `Row` component (likely used for list items/media rows) and a `PlayerDetail` panel (modal/overlay).
3.  **Styling**: The `Row` component currently uses a `<div>` or similar block element for interaction, which is not keyboard accessible by default without event listeners or semantic tags.
4.  **State Management**: There is a global or context-based state for the "Player Detail" panel visibility (e.g., `isDetailOpen`).
5.  **Testing**: Jest/Vitest and Playwright/Cypress are available. The test suite expects specific keyboard interactions (`Enter`, `Space`, `Escape`).

### Risks & Failure Modes
1.  **Double Activation**: If `Row` is made interactive via `<button>` or event listeners, clicking might trigger both mouse and keyboard events redundantly. *Mitigation*: Use semantic `<button>` or ensure event handlers are mutually exclusive or idempotent.
2.  **Focus Trap**: When `PlayerDetail` opens, focus must move into the panel. When it closes, focus must return to the trigger element. *Mitigation*: Implement focus management logic.
3.  **Screen Reader Announcements**: Dynamic content updates (e.g., row selection) may not be announced if not using ARIA live regions or proper role attributes. *Mitigation*: Add `aria-live="polite"` for status updates and `role="button"` if using non-button elements.
4.  **Svelte-Check Warnings**: Removing warnings might involve suppressing false positives. *Mitigation*: Only suppress if the implementation is semantically correct but Svelte-check is overly strict (e.g., missing `tabindex` on custom interactive divs, which we will fix by using `<button>`).
5.  **Edge Case: Multiple Rows**: Keyboard navigation between rows (Up/Down arrows) is not explicitly requested but often expected. *Scope Boundary*: This packet focuses on *activation* (Enter/Space) and *close* (Esc). Arrow key navigation is out of scope unless it breaks existing behavior.

### Implementation Strategy
1.  **Row Component**:
    -   Change the root interactive element from `<div>` to `<button>` (or add `role="button" tabindex="0"` and keyboard event listeners if structural constraints prevent this). *Decision*: Use `<button>` for best accessibility.
    -   Ensure `Enter` and `Space` keys trigger the `click` handler.
    -   Add `aria-label` or ensure text content is sufficient.
2.  **PlayerDetail Panel**:
    -   Add `keydown` listener to the panel or document to catch `Escape`.
    -   Close the panel on `Escape`.
    -   Ensure focus is managed (move to panel on open, return on close).
3.  **Announcements**:
    -   Use `<div aria-live="polite">` for status messages if needed.
    -   Ensure row interactions provide visual and accessible feedback.
